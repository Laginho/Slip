## Top 3

Two findings meet the reporting bar.

### 1. Broken — `src/useSession.ts:118`, `src/store.ts:145`

Each mounted session loads its own list once (`useSession.ts:35`). Mutations operate on
that session's `latest.current` and replace the entire shared localStorage document.
There is no `storage` event subscription or other coordination with another window.
Consequently, a successful save in one window is silently erased by a later save in a
second window that was already open.

**Reproduction:** open two windows on the same local origin with Supabase unset, starting
from the same list. Capture `AUDIT A` in window A; it appears successfully. Capture
`AUDIT B` in window B. Reload A: B is present, A is gone. This was reproduced through
the real UI, and separately with two store snapshots in the temporary Node probe.
The actions are sequential and do not edit the same task.

**Impact:** ordinary use of an installed window alongside a browser tab can lose locally
saved work. With no configured sync, closing/reloading the stale windows removes the
remaining in-memory copy. ADR 0001 accepts concurrent edits to the same task on separate
devices; this failure instead discards distinct tasks on one device and contradicts the
local-first persistence promise. No server behavior is required to trigger it.

**Proposed fix:** coordinate same-origin sessions at the persistence boundary. Before a
mutation, reconcile with the current persisted document using the existing merge rule;
adopt changes received from other windows. Ensure simultaneous read/modify/write operations
cannot interleave, or explicitly enforce one writable session. A `storage` listener alone
does not make read/modify/write atomic. Add a two-context regression that preserves both
captures after reload and exercises an edit/tombstone from the other context.
