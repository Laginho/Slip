## Top 3

### 1. Broken — overlapping round trips can regress remote Task state

Location: `src/useSession.ts:121`, `src/sync.ts:224`; supporting schema: `supabase/schema.sql`.

`roundTrip()` starts requests without an in-flight guard. A mutation's debounce or a foreground/connectivity event can therefore start a second round trip while the first is pending. Each POST unconditionally upserts its earlier merge result. The schema neither compares incoming `updatedAt` against the stored row nor rejects stale writes.

Reproduction: mount one session with an Open Task; hold its initial POST; delete that Task and advance the 1.5-second debounce; allow the second POST to save the tombstone; then allow the first POST to finish. The remote row becomes Open again with its older timestamp. The actual-hook probe confirms localStorage still contains the tombstone, but no additional request occurs over another 60 simulated seconds. A second device receiving that remote row displays the deleted Task until the first device syncs again. Edits and completion state can regress by the same mechanism.

This violates ADR-0001's newer-timestamp convergence and tombstone guarantees under ordinary single-user operation. The existing stale-result tests protect local settlement; they do not protect the remote write order. A passing local merge test does not make an unconditional server upsert monotonic.

Proposed fix: serialize round trips and coalesce triggers received during a flight into one follow-up using the latest state. Add a regression that controls both POST completion order and checks the remote row, not just local state. For protection across tabs/devices as well, enforce the same timestamp/tie winner rule atomically at the server boundary; a per-session guard alone cannot order requests from separate clients.
