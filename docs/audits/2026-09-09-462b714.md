# Audit — slip — 2026-09-09

Verdict: Not approved

Audited by Claude Opus 5

## Summary

Two verified behavioural defects, both reproduced in the running app: completing the
first-ever Task leaves the pull-to-reveal Archive row on screen and shifts the open list
down 56px, and an out-of-range day in the capture bar is silently discarded with no way to
recover the Deadline. Two documents contradict the code they describe: ADR 0002 (`status:
accepted`) specifies a stored Position that does not exist, and DESIGN.md claims to list
the complete colour system while omitting the entire dark chrome. The production source is
otherwise unusually disciplined — no `any`, no type escapes, no non-null assertions, every
non-obvious decision carries its reason in a comment, and 851 tests, `tsc --noEmit` and the
build are all green and all run in CI before deploy. The Slop is small and named below.

## Top 3

### 1. Broken — `src/App.tsx:39-42`

The effect that scrolls the Archive row out of view lists only `archiveOpen` as a
dependency, but its body reads `hasArchive`:

```ts
useEffect(() => {
  if (!hasArchive) return;
  scrollRegionTo(archiveOpen ? 0 : ARCHIVE_HIDDEN_OFFSET);
}, [archiveOpen]);
```

When the Archive goes from empty to non-empty — the user's first-ever completion —
`hasArchive` flips but `archiveOpen` does not, so the effect never runs. `main` grows by
`ARCHIVE_HIDDEN_OFFSET` and the "ver concluídas" row appears at the top with the region
still at `scrollTop: 0`.

**What breaks, when.** Measured in the browser: the first open Card's `top` moves 16 → 72.
Completing a Task pushes the rest of the list down 56px and puts a row on screen that the
design keeps above the fold. That is a direct violation of Product Principle 2 — "Nothing
moves under your eyes. Acting on the list must never reshuffle it" — and of ticket 05's
pull-to-reveal contract. It happens on exactly one path: the transition from zero Done
Tasks to one, which is every new install's first completion, and again after the user
undoes their way back to an empty Archive. Any later Archive toggle silently repairs it,
which is why the existing suite misses it: every row of the "pull to reveal" describe seeds
a Done Task before mounting, so `hasArchive` is already true at first render.

**Fix.** Add `hasArchive` to the dependency list. The early return already handles the
false case, and the ordering is right — the effect runs after the row is in the DOM.

### 2. Broken — `src/components/CaptureBar.tsx:115-122`

```ts
const deadline = dayStr === "" ? null : inferDeadline(Number(dayStr), new Date());
if (!onCapture(text, kind, deadline)) return;
setText("");
setDayStr("");
```

`inferDeadline` returns `null` for anything outside 1–31, and the caller cannot tell that
`null` apart from "the user typed no day at all". The day field accepts two digits, so `0`,
`00` and `32`–`99` all reach it.

**What breaks, when.** Typing `32` — a slip for `3`, `2` or `31` — creates the Task with no
Deadline, clears the field, and shows nothing. Verified end to end in the browser: the
stored record is `{"text":"renovar seguro", ..., "deadline":null}` and no alert is rendered.
This is unrecoverable by design, because PRODUCT.md states that "Editing a Deadline after
capture is deliberately absent", so the only repair is deleting the Task and retyping it —
and the user has no signal that anything went wrong. `create()` in the store applies the
same salvage rule (`storedDeadline = ... : null`), which is right at the storage boundary
but means the mistake is swallowed twice.

**Fix.** Refuse the capture instead of dropping the day: when `dayStr !== ""` and
`inferDeadline` returns `null`, keep everything the user typed and do not call `onCapture` —
the same shape as the existing storage-refusal path, which already leaves the fields intact.
The field can also reject the impossible input as it is typed: the `onChange` guard at line
233 already validates the shape, and extending it to the range costs one comparison.

### 3. Fragile — `docs/adr/0002-manual-position-within-deadline.md:24` vs `src/store.ts:21-29,291`

ADR 0002 is marked `status: accepted`. It states that Position is "the eighth stored field",
that `toTask` must accept it, that a stored Task without one needs a defined fallback, and
that "the Kind tiebreak is retired". None of it exists: `Task` has seven fields, no file in
`src/` mentions `position`, and `openTasks` still returns `KIND_ORDER[a.kind] -
KIND_ORDER[b.kind]` for Tasks sharing a Deadline. `CONTEXT.md:49` carries the same fiction
into the domain vocabulary ("on the desktop the user may drag it to another"), and every
ticket in `.scratch/` is `complete`, so nothing is tracked as outstanding.

**What breaks, when.** Two costs, both live today. First, anyone — human or agent — who
reads the ADR before touching ordering will build on a field that is not there; the ADR even
prescribes migration behaviour ("a stored Task without it needs a defined fallback") for a
migration that never happened. Second, the ordering guarantee CONTEXT.md promises is not
delivered across devices: `merge` returns local Tasks first and remote-only Tasks in
whatever order PostgREST hands back — the GET at `src/sync.ts:114` carries no `order=`
clause — so a fresh install or a cleared cache shows dateless Tasks in arbitrary order.
Verified: seeded rows `c, a, b` render as `terceira | primeira | segunda`.

**Fix.** Decide, and make the documents match. Either implement Position — the ADR already
specifies the whole design, and the schema needs one nullable column — or supersede ADR 0002
with a short `status: superseded` note and revert the `CONTEXT.md` Position entry to the
derived order the code actually implements. Leaving an accepted ADR unimplemented and
untracked is the state that costs the most.

## All findings

- **Broken** `src/App.tsx:39` — the Archive scroll effect omits `hasArchive` from its
  dependencies, so the first completion leaves the pull-to-reveal row on screen and shifts
  the open list down 56px.
- **Broken** `src/components/CaptureBar.tsx:116` — a day outside 1–31 is silently dropped
  and the Task is captured with no Deadline, which cannot then be added.
- **Fragile** `docs/adr/0002-manual-position-within-deadline.md:24` — an accepted ADR
  specifies a stored Position, a `toTask` ingress rule and a retired Kind tiebreak that
  `src/store.ts` does not implement; `CONTEXT.md:49` repeats it as domain vocabulary.
- **Fragile** `DESIGN.md:68` — "These values are the complete colour system, sourced from
  `src/palette.ts`" is false: the five dark-chrome values at `src/palette.ts:78-86`
  (`#1c1b19`, `#262523`, `#3a3835`, `#a8a49e`, `#f2f0ec`) appear nowhere in the document,
  while its own prose says the chrome follows the system colour scheme. A visual pass
  working from DESIGN.md has no dark values to honour and would have to invent them,
  breaking the Palette Is Law rule the same document states.
- **Slop** `src/store.ts:236` — `setDeadline` has no production caller (8 references, all in
  `store.test.ts`); Deadline editing is deliberately absent from the product.
- **Slop 3× `@ts-nocheck` on test files**: `src/identity.test.ts:1`,
  `src/palette-law.test.ts:1`, `src/publish.test.ts:1` — the CI typecheck does not see those
  758 lines, so a rename in `src/` fails there at runtime rather than at build.
- **Slop** `src/testing.tsx:31-88` — four near-identical `matchMedia` stub factories
  differing only in which query returns `true`; one factory taking a predicate replaces all
  four.
- **Slop** `src/components/Card.tsx:340-378` — the same `stopPropagation` + `suppressClick`
  preamble is repeated verbatim in three button handlers.

## Recommended order

1. **Finding 1** — a one-word fix with a reproduction already written, and the only finding
   that misbehaves on a path every user walks.
2. **Finding 2** — small, self-contained, and the failure is silent and permanent, which is
   the worst combination for a product whose fourth principle is that the UI must never
   claim a write it did not make.
3. **Finding 3** — a decision, not a patch. Until it is made, the ordering documentation and
   the ordering code disagree, and every future ordering change starts from a false premise.
4. **Finding 4**, then the Slop. Adding ESLint with the React hooks rules is worth doing
   before the next feature: it turns finding 1's whole class into a build error.
