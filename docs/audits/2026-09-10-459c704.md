## Summary

One behavioural defect: a day field holding `0` makes Capture silently inert — send stays
enabled, Enter does nothing, nothing is stored, nothing is said. That is the far side of
the same door the 2026-09-09 audit opened, whose remediation stopped the silent *drop* but
left the silent *refusal*. Four fragilities, all in the verification layer rather than the
product: `npm test` from the main checkout runs 852 tests, 544 of them from six-day-old
worktrees, and both existing audit records quote that number as evidence; the "Palette Is
Law" guard pins 6 of the 20 frozen colour values; DESIGN.md still specifies a bottom-anchored
phone list the code abandoned several commits ago. The production source itself remains
disciplined — no `any`, no type escapes, no hex outside `src/palette.ts`, and every previous
finding verified fixed.

## Top 3

### 1. Broken — `src/components/CaptureBar.tsx:114-125`

```ts
const capture = () => {
  if (blank) return;
  const deadline = dayStr === "" ? null : inferDeadline(Number(dayStr), new Date());
  if (dayStr !== "" && deadline === null) return;   // <- silent
```

The keystroke guard at line 239 (`/^\d{0,2}$/.test(raw) && Number(raw) <= 31`) deliberately
lets `0` through — it is the first keystroke of `03` — and `00` with it. Both reach
`inferDeadline`, which returns `null` for anything outside 1–31. `capture()` then returns
without a word, and `disabled={blank}` at line 259 keys only off the text, so the send
button stays lit.

**What breaks, when.** The user types a Task, leaves `0` in the day field, and presses send
or Enter. Nothing is stored and nothing is said; the button visibly accepts the press.
Pressing again does the same, forever, because the cause is a character in a 40px field
they are not looking at. Measured in the browser: two Tasks before, two Tasks after, the
document text unchanged. This is Capture — Product Principle 1, "any step added to
typing-and-Enter is wrong" — failing closed with no signal, which is the same class of
failure the 2026-09-09 audit called Broken, inverted: that version silently stored the wrong
thing, this one silently stores nothing. Reaching it needs the field to hold exactly `0` or
`00`, which is one dropped keystroke away from `10`, `20` or `30`.

**Fix.** Make the refusal visible through the control that already expresses refusal. Hoist
the computed deadline out of `capture()` and widen the existing disabled rule:

```ts
const deadline = dayStr === "" ? null : inferDeadline(Number(dayStr), new Date());
const blocked = blank || (dayStr !== "" && deadline === null);
// ...
<button type="submit" aria-label="enviar" disabled={blocked} ...>
```

The send button then dims exactly as it already does for empty text — existing styling,
existing palette, no new colour, no banner — and `capture()`'s silent `return` becomes
unreachable rather than invisible.

### 2. Fragile — `vite.config.ts:64-66` and `package.json:8`

`.claude/worktrees/` and treats every worktree's `src/` as part of the suite:

| Command | Files | Tests |
| --- | --- | --- |
| `npx vitest run --dir src` | 10 | 308 |
| `npm test` | 28 | 852 |

The two worktrees present, `standup-687434` and `standup-fb264f`, are both pinned at
`c4b87ce` (2026-09-04) — several commits and one whole audit remediation behind `main`. 544
of those 852 tests are asserting against code that no longer exists here.

**What breaks, when.** It has already broken. `docs/audits/2026-09-09-462b714.md` records
"28 files, 851 tests, all passing" as the gate result, and
`docs/audits/2026-09-10-remediation.md` repeats "28 files, 851 tests passed (two regressions
added)" as proof the remediation landed. Neither number describes this repository; both

`process.cwd()` — `palette-law.test.ts:14`, `publish.test.ts:7` — so the worktree copies
re-assert the *main* checkout's files while their component tests run stale code: the suite
gets louder and less informative at the same time. `docs/agents/orchestration.md:44-47`
already documents the trap and the workaround, which means every gate run since has depended
on the operator remembering a footnote. CI is unaffected (no worktrees there), so the
divergence is invisible exactly where it would be caught.

**Fix.** Bind the suite to this checkout, in the config rather than in prose:

```ts

```

`npm test` then means the same thing everywhere, and the "27 files instead of 9" paragraph
in `orchestration.md` can be deleted rather than obeyed. Separately, dispose of the two
worktrees: `orchestration.md:34-36` already requires it.

### 3. Fragile — `src/palette-law.test.ts:91-106` vs `PRODUCT.md:59-64`

PRODUCT.md states that "The nine Card swatches are individually immutable" and that "The
remaining exported chrome/ink tokens in `src/palette.ts` are frozen by the same rule";
`DESIGN.md:73` marks the whole colour block **FROZEN**. The guard that enforces this pins
six values: `CARD.work.{light,medium,dark}`, `INK_ON_LIGHT`, `INK_ON_DARK` and
`OVERDUE_RED`.

Searched across every test file, these fourteen frozen values are pinned by nothing:

`#faebc2 #e7ba51 #9d6607` (College) · `#cfe6f7 #4b99d2 #275a86` (Chore) ·
`#8a8783 #e2e0dc #2b2a28 #f7f6f4 #f5f4f2` (light chrome) ·
`#1c1b19 #262523 #f2f0ec #a8a49e #3a3835` (dark chrome).

**What breaks, when.** The component tests read colours *through* the palette —
`rgb(CARD.college.dark)`, `toRgb(CHROME.dark.surface)` — so they follow a change instead of
catching it. Edit College's amber and the suite stays green: 308 passing tests, a violated
brand commitment, and the comment explaining why that amber is `#9d6607` (a 4.84:1 contrast
floor, `src/palette.ts:20-24`) silently obsolete. The predictable change is not
hypothetical: this repo runs visual passes as a matter of routine
(`.scratch/polish-and-publish/issues/04-visual-review.md`), and PRODUCT.md's instruction to
those passes is precisely "never a colour value". Rule 10 in the same test file catches a hex
*leaking out* of `palette.ts`; nothing catches a hex *changing inside* it.

**Fix.** Extend the existing `it("11 — …")` block to assert all twenty values, not six. It
is a literal table in the file that already owns the rule, it costs no new machinery, and it
turns the brand commitment into something the gate can see.

## Recommended order

1. **Finding 1** — the only finding a user meets, on the one interaction the product exists
   for, and the fix is one expression reusing a control that already exists.
2. **Finding 2** — a one-line config change that makes every future gate result mean what it
   says. Do it before the next remediation, or that remediation's evidence is worth what the
   last one's was. Dispose of the two worktrees in the same pass.
3. **Finding 4** — a decision, not a patch: either restore bottom-anchoring or strike it from
   DESIGN.md and the polish spec. Until then the design contract every implementer is
   required to diff against is wrong about the phone, which is the product's primary profile.
4. **Finding 3**, then **finding 5**, then the Slop. Finding 3 is a table of fourteen
   literals in a file that already exists; it is the cheapest way to make a stated brand
   commitment enforceable.
